7. Segurança, Autenticação e Tratamento de Erros
7.1. Autenticação (funcionamento correto)
Senhas nunca armazenadas em texto plano — hash bcrypt (hash(password, 8)).
Login compara hash via compare(), nunca comparação direta de strings.
Token JWT assinado com segredo do servidor (process.env.JWT_SECRET), expira em 1 dia (expiresIn: "1d").
Rotas sensíveis (universidade, mobilidade, usuários por id) exigem o header Authorization: Bearer <token>, validado por authMiddleware.
7.2. Falhas de segurança identificadas (pontos a saber explicar na banca)
POST /user e GET /user sem autenticação (userRoutes.ts): qualquer visitante não autenticado pode criar um usuário com perfil ADMINISTRADOR diretamente via API (mesmo que a tela de cadastro no front não exponha essa opção sem estar logado, a API não impede a chamada direta) e pode listar todos os usuários cadastrados, incluindo emails e universidades vinculadas.
Hash de senha vazando na resposta da API: AuthService.login retorna o objeto user completo do Prisma (incluindo password, o hash bcrypt) na resposta HTTP de login; UserService.findAll faz o mesmo na listagem de usuários usada por CadastroUtilizador.tsx. Embora seja um hash (não a senha em claro), expor hashes desnecessariamente aumenta a superfície de ataque para quebra offline.
CORS liberado para qualquer origem (app.use(cors()) sem origin restrito): em produção, isso permite que qualquer site na internet faça requisições autenticadas à API a partir do navegador de um usuário que tenha um token válido salvo (mitigado parcialmente pelo fato de o token estar em localStorage, não em cookie, então não é enviado automaticamente por outros sites — mas ainda é uma prática recomendada restringir origin para o domínio real do front).
JWT_SECRET não presente no repositório (correto, está no .gitignore via .env), mas também não há validação/fallback caso a variável não exista — se o .env não for configurado, jwt.verify/jwt.sign recebem undefined como secret, o que gera comportamento inesperado (e, dependendo da versão do jsonwebtoken, pode lançar erro em runtime ao invés de falhar de forma controlada).
Regra de negócio de canManageMobility inconsistente: como visto na seção 5.6.5, a rota de mobilidade encadeia isAdmin antes de canManageMobility, então, na prática, apenas administradores conseguem gerenciar mobilidades — o perfil GESTOR_MOBILIDADE (que, pelo nome e pela existência do middleware canManageMobility, deveria ter essa permissão) fica de fato bloqueado. Esse é provavelmente um bug funcional, não uma decisão intencional, pois contraria o próprio propósito do perfil "Gestor de Mobilidade" existir no enum.
sameUniversityOrAdmin nunca utilizado: o middleware que restringiria um Gestor de Mobilidade a operar apenas sobre dados da própria universidade existe no código, mas não está conectado a nenhuma rota — reforça que a segmentação por universidade para o perfil GESTOR_MOBILIDADE está incompleta/não implementada de fato.
Falta de rota protegida no front-end: como não há PrivateRoute, qualquer usuário (mesmo sem login) pode navegar diretamente para as URLs internas; a "proteção" real só acontece no backend (que corretamente recusaria as chamadas de API), mas a UI não comunica isso ao usuário, deixando telas "quebradas" (zeradas, sem redirecionamento) — isso é uma falha de UX, não estritamente de segurança de dados, já que os dados sensíveis continuam protegidos pela API.
Sem função de logout: Sidebar.tsx tem um link "Sair" para /login, mas não há nenhuma chamada localStorage.removeItem("token") em nenhum lugar do código — o token expirado ou de outro usuário pode continuar no localStorage do navegador indefinidamente.
Console.log de debug esquecidos em produção: authMiddleware ("AUTH MIDDLEWARE EXECUTOU"), RankingController.getRanking (console.log(req.query)), UserController.create (console.log(request.body) — loga a senha em texto plano no log do servidor), CadastroMobilidade.tsx (console.log('oi', students)), CadastroUniversidades.tsx (console.log("TOKEN: ", token)), Dashboard.tsx/DashboardInterno.tsx/Rankings.tsx (logs de resposta de API). Nenhum é malicioso, mas todos deveriam ser removidos antes de um deploy de produção — o log de senha em texto plano no UserController.create é o mais sensível.
7.3. Tratamento de erros
Backend: apenas DashboardsController e RankingController usam try/catch, retornando 500 genérico. Todos os outros controllers (AuthController, MobilityController, UniversityController, UserController) não capturam exceções — se um Service lançar erro (ex.: "Universidade não encontrada", "Email ou senha inválidos"), a requisição resulta em erro não tratado. No Express 5 (diferente do 4), handlers assíncronos que rejeitam são automaticamente encaminhados ao error handler padrão do Express, que devolve 500 com detalhes do erro — ou seja, mesmo sem "catch" explícito, a aplicação não trava, mas o cliente recebe um 500 (ao invés de um 400/404 semanticamente correto) para erros que são, na verdade, esperados (ex.: senha errada deveria ser 401, não 500).
Frontend: a maioria dos handleSave/useEffect não trata erros (sem .catch/try-catch), exceto CadastroMobilidade.tsx (handleSave tem try/catch/finally, com alert de erro) e as páginas de dashboard/ranking (try/catch com console.error). Não existe um sistema de notificação (toast) — feedback ao usuário é via alert() nativo (bloqueante, UX datada) ou nenhum feedback algum.
Contrato de erro inconsistente: alguns Services retornam uma string de erro ("Universidade não encontrada") em vez de lançar exceção ou retornar null/status HTTP apropriado (updateMobility, deleteMobility, updateUniversity, deleteUniversity, updateUser, deleteUser no backend) — o Controller então devolve essa string com status 201 (Created) mesmo quando a operação falhou por "não encontrado", o que é semanticamente incorreto (deveria ser 404).
